# 官方飞书能力基线与项目差异化

> 观察日期：2026-09-26  
> 当前证据：用户提供的飞书官网截图；具体 API、套餐、权限和开放程度仍需进入真实测试租户后核验。

用户后续截图进一步显示，飞书应用创建页提供“从智能体模板开始”，说明模板可预置智能体所需的权限和事件配置，并列出 OpenClaw、Hermes Agent 等接入对象。这是比产品宣传页更接近实际配置入口的证据，但仍不等于目标租户已经验证了具体 API、权限范围和审计能力。

## 1. 截图中观察到的官方能力

截图显示飞书当前已经提供或展示了以下相关能力：

| 官方能力 | 与本项目的重叠 | 本项目不应重复实现的部分 | 本项目仍研究的部分 |
|---|---|---|---|
| 智能会议纪要 M4 | 会议内容记录、摘要和会议资产 | 通用录音转写、普通摘要 | 待办证据、责任人确认、权限交集、任务落实、审计和失败对账 |
| 豆包工作 / 豆包工作伙伴 | 个人助手、Agent 协作 | 通用聊天助手和基础办公问答 | 个人助手如何受组织策略约束、如何委托共享业务 Agent、如何保留治理轨迹 |
| 飞书 OpenClaw 插件 | 本地 Agent 与飞书连接 | 本地 Agent 的通用连接能力 | 本地 Agent 的身份边界、工具策略、审批和服务器控制平面接入 |
| 飞书 CLI | Agent 操作飞书资源 | CLI 本身和基础命令封装 | CLI/Runtime 作为受控执行器时的权限、审计、幂等和恢复 |
| 飞书 aPaaS | 企业应用、业务 Agent、管理界面 | 通用低代码 CRUD 和通用应用搭建 | 面向多 Agent 组织治理的领域模型、不可变版本、审批绑定和跨 Runtime 控制 |
| 多维表格 AI、项目 AI 等 | 某些业务自动化能力 | 通用表格或项目管理功能 | 将多个官方能力组合成可解释、可审计的 Agent 工作流 |

上表是定位分析，不代表已经确认这些产品全部支持本项目所需的开放接口。正式实施前必须记录官方文档链接、目标租户可用权限和实测结果。

## 2. 项目重新定位

本项目不是再做一个“飞书版会议纪要”，也不是再做一个通用办公助手。更准确的定位是：

> **飞书之上的小型多 Agent 组织治理与业务落地实验系统。**

飞书官方能力作为企业数据、交互和部分 Agent 能力底座；Hermes、OpenClaw 或飞书 CLI 作为可替换执行器；自研控制平面负责把这些能力组织起来，并处理官方产品通常不会替本项目完成的治理问题：

```text
谁可以调用哪个 Agent
Agent 可以看到哪些数据
高风险动作谁来确认
多个 Runtime 如何统一执行轨迹
写入超时如何对账
Agent 和 Skill 如何审核、版本化、回滚
知识冲突如何保留来源并转人工
```

## 3. 会议场景的调整

会议仍然是第一条业务切片，但目标从“证明我们能转录会议”调整为“证明会议结果可以安全、可追溯地落实”。输入可以有两条路径：

```text
路径 A：飞书智能会议纪要/官方会议产物
      → 读取授权结果 → 提取待办 → 人工确认 → 创建任务 → 审计

路径 B：授权录音
      → 自有 ASR 适配器 → 提取待办 → 人工确认 → 创建任务 → 审计
```

路径 A 优先用于真实演示，减少重复造轮子；路径 B 用于研究自有 ASR 适配和降级能力。两条路径最后都必须经过同一个权限、审批、工具网关和审计流程。

因此，会议 Agent 的核心验收不再是“摘要比飞书更好”，而是：

1. 每条待办能引用原文或时间证据；
2. 责任人和可见范围不明确时会补问或转人工；
3. 创建任务前必须由有权限的人确认；
4. 重复回调、审批篡改和写入未知结果不会造成重复任务；
5. 官方产物和自有 ASR 产物都能进入同一条可审计流程。

## 4. Runtime 与官方产品的关系

飞书 OpenClaw 插件、飞书 CLI、Hermes 都不直接等于本项目的控制平面。它们可以放在 `RuntimeAdapter` 或工具执行器之后：

```text
飞书入口 / 官方能力
        ↓
自研控制平面：身份、权限、审批、TaskRun、审计、对账
        ↓
RuntimeAdapter
        ├── Hermes
        ├── OpenClaw / 飞书 OpenClaw 插件
        └── 飞书 CLI 或其他受控执行器
```

执行器不能因为来自飞书官方就自动获得全部权限；仍然必须经过本项目的权限交集、ToolPolicy 和人工确认。

## 4.1 是否调用飞书官方 Agent

可以把飞书官方 Agent 作为外部 Agent 接入，但不能仅凭官网页面判断“可以直接调用”。需要先确认它是否提供以下任一受支持入口：

```text
开放 API / HTTP
MCP 工具
A2A Agent Card 或任务接口
飞书工作流/事件触发器
官方 CLI 或 OpenClaw 插件命令
```

根据开放程度分三种情况：

| 官方 Agent 暴露方式 | 我们的接入方式 | 结论 |
|---|---|---|
| 有结构化 API、MCP 或 A2A | 实现 `ExternalAgentAdapter`，转换为内部 `Delegation`/`TaskRun` | 可以作为正式候选 |
| 只能通过工作流、机器人消息或事件触发 | 做异步消息适配，等待结构化结果和回调 | 可以演示，但需重点验证幂等和超时 |
| 只能在网页界面人工操作 | 不做 UI 爬取或模拟点击 | 暂不接入，保留为人工步骤 |

即使官方 Agent 被成功调用，它返回的文本、摘要或建议也只是不可信的外部产物，不能直接改变本项目的权限、审批或写入决策。调用过程必须记录：调用者、用户身份、官方 Agent 版本/标识、输入引用、输出摘要、状态、耗时和错误。

推荐的第一条组合流程是：

```text
用户在飞书提交会议请求
→ 我们的会议编排 Agent
→ 调用飞书会议纪要 Agent（如果开放接口可用）
→ 得到带来源的会议产物
→ 我们提取待办并检查权限
→ 飞书卡片人工确认
→ 创建飞书任务并审计
```

这样飞书官方 Agent 负责它擅长的会议理解，我们的 Agent 负责组织治理和安全落实。

标准 A2A 不是强制条件：官方 Agent 支持 A2A 时可以使用 A2A Adapter；不支持时使用 HTTP、SDK、MCP、工作流或 CLI Adapter，但都要先转换为内部 `TaskRun`，不能让外部协议绕过控制平面。

## 4.2 企业中的 Agent 注册表

用户提供的飞书界面截图显示，企业空间中已经同时存在豆包工作、官方飞书助手、普通机器人和标记为“智能体”的 Agent。它们可以作为本项目的外部 Agent 候选，但需要在控制平面中登记，而不是直接把聊天列表当成可调用接口。

每个候选 Agent 至少登记以下信息：

```text
agent_id / 展示名称 / 来源
能力标签：会议、文档、任务、开发等
调用入口：chat_event / workflow / http / mcp / a2a / cli / manual
输入和输出 schema
所属用户或团队
可见数据范围
允许的风险级别
版本、状态和健康检查方式
```

编排流程为：

```text
用户请求
→ 我们的路由器查询 Agent 注册表
→ 选择有权限且能力匹配的 Agent
→ ExternalAgentAdapter 调用
→ 返回结果进入控制平面
→ 权限/审批/审计/对账
```

如果某个 Agent 只能在飞书界面里人工聊天，没有开放 API、事件、工作流或 CLI，就标记为 `manual`，不能通过模拟点击或抓取界面强行自动化。这样既尊重平台边界，也让系统能明确告诉用户“当前需要人工转达”。

## 5. 对毕设和求职的影响

这个变化不会削弱项目，反而使研究问题更真实。答辩时可以明确说明：

> 飞书已经提供会议纪要、办公助手和 Agent 连接能力，因此本项目没有重复实现这些基础产品，而是把它们当作企业底座，研究多个 Agent 和 Runtime 接入后如何进行权限治理、事前审批、任务恢复、审计和 Skill 生命周期管理，并用会议任务落实作为可演示的垂直场景。

这种定位比“自己做一个会议纪要工具”更符合 FDE 的工作：识别已有平台能力，选择复用边界，再补上企业落地所缺的治理和业务闭环。
